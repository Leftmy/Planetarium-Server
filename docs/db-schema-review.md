# Ревʼю схеми БД — Planetarium

Розбір запропонованої структури бази під продуктові вимоги з [README](../README.md) та архітектурний напрям (vertical slicing).

**Загальна оцінка:** схема добре покриває всі три P0-фічі, сутності виділені логічно, `jsonb` стоїть у правильних місцях, ключові unique-обмеження на парах `user + node` вже передбачені. Нижче — те, що варто закрити до першої міграції.

Пункти згруповані за пріоритетом:

| Розділ | Що це означає |
|---|---|
| [Блокери](#блокери) | Зачеплять P0, дешевше виправити до першої міграції |
| [Важливе](#важливе-але-не-блокує) | Не блокує старт, але вилізе на реальних даних |
| [Архітектура](#як-це-лягає-на-вертикальні-зрізи) | Як сутності лягають на слайси і де головний ризик |
| [Чек-лист](#чек-лист) | Стислий підсумок для трекера |

---

## Блокери

### 1. `User.provider` не працює для OAuth

**Проблема.** У схемі немає поля з ідентифікатором користувача на стороні провайдера (`sub` у Google, `id` у GitHub). Єдиний спосіб знайти акаунт при OAuth-логіні — за email, а це небезпечно: GitHub віддає email, які можуть бути неверифікованими або приватними. Це класичний вектор захоплення акаунта — зловмисник реєструє в провайдера адресу, що вже існує у вас, і входить у чужий профіль.

Друга частина проблеми: `provider` як колонка на `User` жорстко привʼязує акаунт до одного способу входу. Людина, що зареєструвалась через email+пароль, не зможе потім увійти через Google на ту саму адресу — `email` unique не дасть створити другий запис.

**Рішення.** Винести ідентичності в окрему таблицю:

```sql
CREATE TABLE user_identity (
    id               UUID PRIMARY KEY,
    user_id          UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    provider         TEXT NOT NULL,          -- local | google | github
    provider_user_id TEXT NOT NULL,          -- sub / id від провайдера
    email            TEXT,
    created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),

    UNIQUE (provider, provider_user_id)
);
```

`password_hash` лишається на `User` (або переїжджає сюди для `provider='local'`), а колонка `provider` з `User` прибирається. Один користувач отримує кілька способів входу безкоштовно.

---

### 2. Дерево навичок не має ребер

**Проблема.** `SkillNode` має `tier`, але tier — це **глибина**, а не звʼязок. За ним неможливо відповісти на запитання «які вузли розблокує цей». Стани `locked → available` з `SkillNodeState` без ребер обчислити не можна — інформації про залежності в схемі просто немає.

**Рішення.** Або `parent_id` на `SkillNode` (якщо це строге дерево), або окрема таблиця залежностей за зразком `NodeDependency`:

```sql
CREATE TABLE skill_node_dependency (
    id                     UUID PRIMARY KEY,
    skill_node_id          UUID NOT NULL REFERENCES skill_node(id) ON DELETE CASCADE,
    depends_on_skill_node_id UUID NOT NULL REFERENCES skill_node(id) ON DELETE CASCADE,

    UNIQUE (skill_node_id, depends_on_skill_node_id),
    CHECK  (skill_node_id <> depends_on_skill_node_id)
);
```

Для скіл-дерев зазвичай потрібен саме DAG, а не дерево — вузол може мати кілька передумов («Горутини» вимагають і «Конкурентність», і «Канали»). `parent_id` такого не виражає, тому таблиця залежностей гнучкіша.

**Супутнє.** Сумарних скіл-поінтів користувача ніде немає. Або поле на `User`, або завжди `SUM` по mastered-станах через join на `SkillNode.skill_points`. Друге чесніше (немає розсинхрону), але для дашборду профілю з P1 варто кешувати.

---

### 3. `QuizAttempt.questions` містить еталонні відповіді поруч із питаннями

**Проблема.** У полі лежать «згенеровані питання (+еталонні відповіді)». Якщо хендлер віддасть сутність цілком — наприклад, у відповіді на створення спроби або в `GET /attempts/{id}` — тест зламано ще до того, як користувач відповів.

**Рішення.** Або розділити на дві колонки (`questions_public` і `answer_key`), або дуже дисципліновані DTO. Vertical slicing тут якраз допомагає: слайс `quiz` має власний `dto.go`, і доменна сутність назовні не виходить — рівно як зроблено в [register/dto.go](../internal/user/register/dto.go) на гілці `feature/initial-folder-structure`. Але це треба зафіксувати як правило зараз, а не після інциденту.

Розділення на дві колонки надійніше: воно робить помилку неможливою, а не просто малоймовірною.

---

### 4. `NodeDependency` без захисту від циклів

**Проблема.** Немає жодного з трьох обмежень:
- `unique (node_id, depends_on_node_id)` — дублікати залежностей;
- `CHECK (node_id <> depends_on_node_id)` — вузол як власна передумова;
- гарантії, що обидва вузли належать одному роадмапу — FK дивиться просто на `RoadmapNode`, тож залежність може вести в чужий роадмап.

Цикл у графі підвісить обхід, який обчислює доступність вузла — а помилка `ErrNodeLocked` для цього вже оголошена в [errors.go](../internal/domain/errors.go).

**Рішення.** Перші два закриваються на рівні БД:

```sql
ALTER TABLE node_dependency
    ADD CONSTRAINT node_dependency_uniq UNIQUE (node_id, depends_on_node_id),
    ADD CONSTRAINT node_dependency_no_self CHECK (node_id <> depends_on_node_id);
```

Ациклічність — валідацією в usecase перед комітом (обхід у глибину по майбутньому стану графа). «Один роадмап» — або композитним FK через `UNIQUE (id, roadmap_id)` на `RoadmapNode`, або теж валідацією в usecase.

---

### 5. Редагування роадмапу під користувачами, які його проходять

**Проблема.** Автор публічного роадмапу видаляє або переставляє вузли. Що відбувається з чужим `NodeProgress` і закешованим `completion_pct`? Зараз прогрес просто зникає, відсоток стрибає, а користувач бачить, що «втратив» пройдене.

Це не баг схеми, а продуктове рішення — але воно **змінює схему** залежно від вибору:

| Варіант | Що додається | Ціна |
|---|---|---|
| Заборонити структурні правки опублікованого | нічого, тільки перевірка в usecase | найдешевше, автор змушений форкати |
| Версіонування | `Roadmap.version`, прогрес привʼязаний до версії | складна міграція прогресу між версіями |
| Копія при старті | `UserRoadmap` тягне приватний знімок вузлів | дублювання даних, форк оновлень не отримає |

Для MVP найдешевший — перший: дозволити редагувати вміст (назви, описи, ресурси), заборонити структурні зміни (додавання/видалення вузлів, зміну залежностей) після публікації, а для реальних змін — форк.

## Важливе, але не блокує

### `group` — зарезервоване слово в PostgreSQL

Колонку `RoadmapNode.group` доведеться квотити як `"group"` у **кожному** запиті, інакше синтаксична помилка. Перейменувати на `group_name` або `section`.

### Індекси під анти-фарм

Ліміт спроб і кулдаун із P0 — це запит «останні N спроб цього юзера по цьому вузлу». Без індексу він деградує рівно тоді, коли продукт почне рости:

```sql
CREATE INDEX quiz_attempt_user_node_idx
    ON quiz_attempt (user_id, node_id, created_at DESC);
```

Для каталогу роадмапів із пошуком і фільтрами знадобиться індекс на `(visibility, category, difficulty)`.

### Бракує unique-обмежень

- `UserRoadmap (user_id, roadmap_id)` — інакше подвійний клік по «Почати» створить два записи прогресу.
- `Achievement (user_id, type)` — інакше «first_quiz» видасться двічі при гонці двох паралельних запитів. Якщо ачівки бувають повторюваними, потрібен окремий прапорець або лічильник замість unique.
- `RoadmapNode (roadmap_id, order_index)` — захистить від колізій порядку.

### `order_index` як `int` незручний для білдера

Drag-and-drop із P1: вставка вузла між двома сусідніми переписує весь хвіст таблиці. `float` (або fractional indexing — беремо середнє між сусідами) вирішує це одним `UPDATE`.

### `timestamptz`, не `timestamp`

Особливо для `last_activity_at`: streak рахується по днях, і без визначеної таймзони «день» у користувача і на сервері різні — людина втрачатиме streak через зсув. Заодно варто вирішити зараз, у чиїй таймзоні він рахується (UTC найпростіше, таймзона профілю — правильніше для користувача).

### Політика видалення

- `Roadmap.forked_from` → `ON DELETE SET NULL`, інакше видалення оригіналу вбʼє всі форки.
- Для `Roadmap` загалом — soft delete (`deleted_at`), бо на нього висить чужий прогрес і чужі форки.
- Для `RoadmapNode` → `ON DELETE CASCADE` на `NodeResource` і `NodeDependency` виглядає безпечно, а от на `NodeProgress` — ні (див. блокер 5).

### `completion_pct` — кеш без визначеного моменту перерахунку

Оновлювати в **тій самій транзакції**, що й `NodeProgress`, інакше відсоток розійдеться з реальністю. Варто передбачити фонову звірку.

### Гостьовий режим із P0 не представлений

Якщо гість може відмічати вузли — його прогрес десь має жити. Найпростіше: `localStorage` на клієнті з міграцією в БД при реєстрації. Але це рішення треба ухвалити явно, бо воно впливає на контракт API.

### Дрібне

- `created_at` / `updated_at` відсутні на більшості таблиць — `NodeProgress` має `completed_at`, але не має `updated_at`.
- `Achievement.type` як вільний рядок відкриває шлях до одруківок. Або enum, або довідкова таблиця з описом і іконкою (все одно знадобиться для UI).

## Як це лягає на вертикальні зрізи

Сутності групуються по слайсах майже без залишку:

```
internal/domain/         User, Roadmap, RoadmapNode, Email, errors  — спільне ядро
internal/user/           register, login, oauth      → User, UserIdentity
internal/roadmap/        catalog, get, create, fork   → Roadmap, RoadmapNode,
                                                        NodeDependency, NodeResource
internal/progress/       enroll, start_node, complete → UserRoadmap, NodeProgress
internal/quiz/           generate, submit             → QuizAttempt
internal/skilltree/      get, recalc                  → SkillNode, SkillNodeState
internal/achievement/    grant, list                  → Achievement
```

### Головний ризик

Проходження тесту запускає ланцюжок через **чотири слайси**:

```
quiz.submit → progress (вузол completed) → skilltree (перерахунок станів) → achievement (перевірка ачівок)
```

Якщо кожен слайс імпортуватиме наступний напряму, ви швидко отримаєте циклічні імпорти й розмиті межі — рівно те, проти чого vertical slicing і задумано.

**Два робочі варіанти:**

1. **Доменні події.** `quiz` публікує `NodeCompleted`, підписники (`skilltree`, `achievement`) реагують. Чисто, легко тестується ізольовано, але для MVP може бути надлишково.
2. **Явний оркестратор.** Usecase у `progress`, який приймає результат тесту й викликає `skilltree` / `achievement` через інтерфейси, **оголошені в самому `progress`**. Простіше, і виглядає природно, бо прогрес тут і є центром доменної моделі.

Для MVP розумніший другий варіант — перехід на події потім буде механічним.

### Інтерфейси репозиторіїв

Інтерфейс сховища оголошує **usecase**, а `internal/adapter/postgres` його реалізує — так, як уже зроблено з `registerUsecase` у [register/handler.go](../internal/user/register/handler.go), де інтерфейс оголошує споживач. Інакше вертикальні зрізи почнуть тягнути `pgx` напряму й ізоляція зникне.

### Спільні дані між слайсами

`NodeProgress` читають `progress`, `skilltree` і `quiz` (для анти-фарму). Це класичне місце, де vertical slicing починає дублюватися. Правило: **власник таблиці — один слайс**, решта ходять через його usecase-інтерфейс, а не в БД напряму.

# Частина 2. Чого в схемі немає взагалі

Розділи вище перевіряють **коректність** наявних сутностей. Але кілька шарів, без яких P0 фізично не поїде, у схемі просто відсутні.

## A. Аутентифікація: немає нічого, крім користувача

`User` зберігає `password_hash` — і на цьому все. Для робочого логіну бракує:

**Сесії або refresh-токени.** Це розвилка, яку треба пройти свідомо:

| Підхід | Плюси | Мінуси |
|---|---|---|
| Stateless JWT без сховища | нуль запитів до БД на валідації | **неможливо відкликати** — розлогінити, забанити, вигнати вкрадену сесію |
| Refresh-токени в БД | повний контроль, список активних пристроїв | +1 запит на оновлення токена |

Для платформи з OAuth і майбутньою модерацією контенту (P2) я б брав другий. Мінімальна таблиця:

```sql
CREATE TABLE refresh_token (
    id          UUID PRIMARY KEY,
    user_id     UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    token_hash  TEXT NOT NULL UNIQUE,   -- зберігаємо хеш, не сам токен
    user_agent  TEXT,
    ip          INET,
    expires_at  TIMESTAMPTZ NOT NULL,
    revoked_at  TIMESTAMPTZ,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX refresh_token_user_idx ON refresh_token (user_id) WHERE revoked_at IS NULL;
```

Токен зберігається **хешованим** з тієї ж причини, що й пароль: дамп БД не має давати доступ до живих сесій.

**Верифікація email і скидання пароля.** Обидва потоки потребують одноразових токенів з TTL. Можна однією таблицею:

```sql
CREATE TABLE user_token (
    id         UUID PRIMARY KEY,
    user_id    UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    purpose    TEXT NOT NULL,          -- email_verify | password_reset
    token_hash TEXT NOT NULL UNIQUE,
    expires_at TIMESTAMPTZ NOT NULL,
    used_at    TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

Плюс поле `email_verified_at` на `User` — інакше неможливо відрізнити підтверджену адресу від введеної навмання, а це прямо повʼязано з ризиком захоплення акаунта з блокера 1.

**Хешування пароля.** У схемі просто `password_hash string`. Рекомендація: **argon2id** (`golang.org/x/crypto/argon2`) або bcrypt із cost ≥ 12. Параметри алгоритму варто зберігати в самому рядку хешу (стандартний формат `$argon2id$v=19$m=...`), щоб їх можна було підняти без міграції — інакше зміна параметрів зламає всі старі паролі.

## B. AI-модуль: найдорожча прогалина

Зараз `QuizAttempt.questions` каже «згенеровані питання». З цього випливає, що **кожна спроба кожного користувача = окремий виклик OpenAI**. Це проблема одразу з трьох боків:

- **Гроші.** Кількість генерацій росте як `користувачі × вузли × спроби`. На тисячі активних юзерів це вже помітна стаття витрат, і вона лінійно масштабується з успіхом продукту — тобто найгірше саме тоді, коли все йде добре.
- **Затримка.** Генерація тесту — це секунди. Користувач тисне «Пройти тест» і чекає на спінер, поки модель думає. Для гейміфікованого продукту, де тести проходять часто, це відчутно псує відчуття.
- **Недетермінованість.** Двоє користувачів отримують різні за складністю тести на одному вузлі. Порівнювати їхні результати, будувати рейтинги чи апелювати оцінку стає неможливо.

**Рішення — пул питань замість генерації на льоту:**

```sql
CREATE TABLE quiz_question (
    id           UUID PRIMARY KEY,
    node_id      UUID NOT NULL REFERENCES roadmap_node(id) ON DELETE CASCADE,
    payload      JSONB NOT NULL,   -- текст питання, варіанти
    answer_key   JSONB NOT NULL,   -- правильна відповідь; НІКОЛИ не виходить назовні
    difficulty   TEXT NOT NULL,
    model        TEXT NOT NULL,    -- яка модель згенерувала
    prompt_version TEXT NOT NULL,  -- яка версія промпту
    is_active    BOOLEAN NOT NULL DEFAULT true,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX quiz_question_node_active_idx ON quiz_question (node_id) WHERE is_active;
```

Тоді `QuizAttempt` посилається на вибрані `question_id`, а не носить питання в собі:

```sql
CREATE TABLE quiz_attempt_question (
    attempt_id  UUID NOT NULL REFERENCES quiz_attempt(id) ON DELETE CASCADE,
    question_id UUID NOT NULL REFERENCES quiz_question(id),
    user_answer JSONB,
    is_correct  BOOLEAN,
    PRIMARY KEY (attempt_id, question_id)
);
```

Що це дає, крім економії:

1. **Блокер 3 зникає структурно.** `answer_key` живе в іншій таблиці, яку хендлер спроби просто не читає. Витік стає неможливим, а не «малоймовірним».
2. **Анти-фарм стає реальним.** Ключова вимога — не показувати ті самі питання на повторній спробі. З пулом це `WHERE id NOT IN (питання попередніх спроб)`. З генерацією на льоту — ніяк.
3. **Генерація стає фоновою.** Пул наповнюється при створенні вузла або воркером, користувач ніколи не чекає на модель.
4. **Питання можна модерувати.** Модель генерує дурницю — ставите `is_active = false`, і воно зникає з ротації без міграції.

**Що лишається генерувати онлайн:** розбір помилок (`feedback`). Він персональний і кешуванню не піддається — але це вже після відповіді, коли затримка не блокує UX.

**Версіонування моделі та промпту.** Поля `model` і `prompt_version` потрібні не для краси: коли користувач скаржиться «мене неправильно оцінили», без них неможливо відтворити, що саме сталося. Ті самі поля варто продублювати на `QuizAttempt` — модель могла змінитись між генерацією питання й оцінюванням відповіді.

**Облік витрат.** Якщо є бюджет на OpenAI, витрати треба бачити:

```sql
ALTER TABLE quiz_attempt
    ADD COLUMN prompt_tokens     INT,
    ADD COLUMN completion_tokens INT;
```

Без цього ви дізнаєтесь про перевитрату з рахунку, а не з дашборду.

**Ідемпотентність сабміту.** Подвійний клік або ретрай мережі не має створювати дві спроби й списувати дві генерації. Найпростіше — `idempotency_key TEXT UNIQUE` на `QuizAttempt`, який клієнт генерує перед відправкою.

## C. Streak: `last_activity_at` його не порахує

`UserRoadmap.last_activity_at` каже, **коли** була остання активність, але не каже, чи були активності в кожен із попередніх днів. Порахувати «поточний streak = 5 днів» з нього неможливо. А streak прямо заявлений у P1 як частина профілю.

Найдешевше рішення — таблиця днів активності:

```sql
CREATE TABLE user_activity_day (
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    day     DATE NOT NULL,
    PRIMARY KEY (user_id, day)
);
```

Один рядок на день на користувача, вставка через `ON CONFLICT DO NOTHING`. Це дає:
- точний поточний і найдовший streak, який завжди можна **перерахувати** (кешовані лічильники рано чи пізно розходяться);
- heatmap-календар у профілі — той самий, що на GitHub, безкоштовно;
- аналітику утримання без окремої системи.

Обсяг мізерний: 365 рядків на активного користувача на рік.

Тут же вирішується питання таймзони з попереднього розділу: `day` обчислюється в таймзоні користувача, тож її треба зберігати на `User` (`timezone TEXT`).

## D. Каталог і пошук

**`Roadmap.category` як вільний рядок** призведе до `"Programming"`, `"programming"`, `"Програмування"` в одній таблиці за перший же місяць. Для фільтра з фіксованим списком категорій потрібна довідкова таблиця — вона все одно знадобиться, щоб зберігати локалізовану назву, іконку й порядок у меню.

**Пошук.** README обіцяє пошук по каталогу. `ILIKE '%текст%'` не використовує звичайний індекс і на кількох тисячах роадмапів почне гальмувати. Варіанти:

| Підхід | Коли брати |
|---|---|
| `pg_trgm` + GIN | пошук по підрядку, стійкий до одруківок; найпростіше |
| `tsvector` + GIN | повноцінний повнотекстовий, зі стемінгом |
| Зовнішній рушій | не для цього етапу |

Для MVP `pg_trgm` дає найкраще співвідношення користі до складності. Українська морфологія в `tsvector` з коробки не працює добре, тож перевага ще й у цьому.

# Частина 3. Рішення, які дорого відкочувати

Ці речі не «баги» — але змінити їх після того, як накопичаться дані, буде значно дорожче, ніж вирішити зараз.

## UUIDv7 замість UUIDv4

Проєкт уже тягне `github.com/google/uuid` (див. `go.sum`). За замовчуванням усі беруть `uuid.New()` — це **v4, повністю випадковий**. Для первинних ключів це має конкретну ціну: випадкові значення розкидані по всьому B-tree, тож кожна вставка б'є у випадкову сторінку індексу. На таблицях з інтенсивною вставкою (`QuizAttempt`, `NodeProgress`, `user_activity_day`) це дає розпухання індексу й гірший кеш.

`uuid.NewV7()` (доступний у v1.6.0, яка вже в `go.sum`) генерує **впорядковані за часом** ідентифікатори: вставки йдуть у кінець індексу, локальність відновлюється. Зовні це той самий UUID — API не змінюється, міграція не потрібна.

Ціна: v7 розкриває час створення запису. Для цього продукту це не проблема (`created_at` і так є). Рекомендація: v7 скрізь.

## Enum: `TEXT` + `CHECK`, а не нативний тип PostgreSQL

У схемі багато enum-полів: `provider`, `difficulty`, `visibility`, `status`, `state`, `type`. Спокуса — оголосити їх нативними типами PostgreSQL. Не варто: нативний enum **не дозволяє видалити значення** взагалі, а додавання й перейменування створюють проблеми в міграціях.

`TEXT` + `CHECK (status IN (...))` дає ту саму гарантію цілісності, але змінюється звичайним `ALTER TABLE` в межах транзакції. А там, де значення несе метадані (категорії, типи ачівок, типи ресурсів), правильна відповідь — довідкова таблиця, а не enum узагалі.

## Версіонування jsonb-навантажень

У схемі чотири `jsonb`-поля: `quiz_config`, `questions`, `answers`, `feedback`. У них немає схеми — і це нормально, поки формат не змінився. А він зміниться: додасте новий тип питання, поміняєте структуру фідбеку.

Дешева страховка — поле `schema_version` **усередині** самого JSON. Тоді код читає старі записи за старими правилами замість того, щоб падати на несподіваній структурі. Без цього єдиний вихід — міграція, яка переписує всі історичні рядки.

## Іменування

Зафіксувати до першої міграції, бо потім це масове перейменування: `snake_case`, таблиці в однині чи множині (я б брав однину: `user`, `roadmap_node` — хоча `user` доведеться квотити, бо це теж зарезервоване слово; тоді послідовніше множина: `users`, `roadmaps`), FK як `<таблиця>_id`, індекси як `<таблиця>_<колонки>_idx`.

# Частина 4. Інфраструктура — те, чого бракує в репозиторії

## У `docker-compose.yml` немає PostgreSQL

Це не схема, але блокує роботу з нею. Поточний compose (і на `main`, і на `feature/initial-folder-structure`) містить **тільки сервіс `app`**, тоді як `.env.example` уже описує `DB_HOST`, `DB_PORT`, `DB_USER`. Тобто підняти проєкт із базою однією командою зараз неможливо — кожен розробник ставить Postgres руками, з різними версіями.

Потрібен сервіс бази з іменованим томом, healthcheck і `depends_on: condition: service_healthy` — інакше застосунок стартує швидше за базу й падає на першому підключенні.

## Інструмент міграцій

Вибрати треба зараз, бо це визначає формат файлів:

| Інструмент | Особливості |
|---|---|
| `golang-migrate` | найпоширеніший, окремі `.up.sql` / `.down.sql`, є CLI |
| `goose` | міграції можна писати на Go, зручно для складних перетворень даних |
| `atlas` | декларативний, генерує міграції з різниці схем |

Для цього проєкту `goose` виглядає доречно: рано чи пізно знадобиться міграція, що не виражається чистим SQL (наприклад, перенос `provider` з `User` у `UserIdentity`).

Практичні поради, незалежні від вибору:
- вкладати міграції в бінарник через `embed.FS` — тоді Docker-образ самодостатній;
- запускати їх **окремим кроком**, а не при старті застосунку: інакше кілька реплік почнуть мігрувати одночасно;
- писати `down`-міграції з першого дня, поки це дешево.

## Тести проти реальної бази

`.env.example` уже містить `DB_NAME=planetarium_test_db` — намір є. Найкращий варіант для Go — **testcontainers-go**: піднімає справжній Postgres у Docker на час тестів. Моки репозиторіїв не ловлять помилки в SQL, обмеженнях і транзакціях — тобто рівно те, що складає більшість багів шару даних.

Це також дасть змістовне наповнення для кроку `go test ./...` у CI, який зараз проходить лише тому, що тестів немає.

## Транзакційні межі

З пулу питань і ланцюжка «тест → прогрес → скіл-дерево → ачівки» випливає, що одна бізнес-операція чіпає кілька таблиць у кількох слайсах. Це має бути **одна транзакція**, інакше збій посередині лишить користувача з зарахованим тестом і незарахованим скіл-поінтом.

У Go з `pgx` це зазвичай вирішують так: usecase отримує абстракцію, яка вміє виконати функцію в транзакції, а репозиторії працюють з інтерфейсом, який реалізують і `*pgxpool.Pool`, і `pgx.Tx`. Тоді той самий код репозиторію працює і всередині транзакції, і поза нею.

Вирішити це варто **до** написання першого репозиторію — вкручувати транзакції в готовий код болісно.

## Не в схемі (P2, очікувано)
