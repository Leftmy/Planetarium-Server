## Спільне для всіх ендпоінтів

Базовий шлях `/api/v1`. Тіла запитів і відповідей — JSON, `Content-Type: application/json`.

### Формат помилки

Один формат на весь API. Це головне, заради чого існує BE-04: якщо реєстрація віддає
`{"error": "..."}`, а логін `{"message": "..."}`, фронтенд пише два обробники для сусідніх
ендпоінтів.

```json
{
  "error": {
    "code": "email_already_exists",
    "message": "User with this email already exists"
  }
}
```

- `code` — стабільний машинний ідентифікатор у `snake_case`. Фронтенд розгалужується по ньому.
- `message` — англійською, для розробника й логів. **Не** для показу користувачу: локалізація
  на клієнті, за `code`.

Коди помилок для цього тижня:

| HTTP | `code` | Коли |
|---|---|---|
| 400 | `invalid_request` | тіло не парситься або поле відсутнє |
| 400 | `invalid_email` | `domain.ErrInvalidEmail` |
| 400 | `password_too_weak` | `domain.ErrPasswordWeak` |
| 401 | `invalid_credentials` | логін: невірний email **або** пароль (однакова відповідь) |
| 401 | `invalid_refresh_token` | refresh: токен невідомий, протермінований або відкликаний |
| 409 | `email_already_exists` | `domain.ErrAlreadyExists` при реєстрації |
| 500 | `internal_error` | усе інше; деталі йдуть у лог, не в тіло |

Валідація кількох полів одночасно повертає **першу** помилку, а не список. Перелік полів —
коли з'явиться форма профілю; для двох полів це зайва складність. **(?)**

## Токени

| Токен | Тип | TTL | Де живе |
|---|---|---|---|
| access | JWT, HS256 | 15 хв | тіло відповіді, далі `Authorization: Bearer <token>` |
| refresh | випадкові 32 байти, base64url | 30 днів | **(?)** тіло або httpOnly-cookie |

Refresh навмисно **не** JWT: його сенс у тому, що він лежить у базі і його можна відкликати.
JWT відкликати не можна, не завівши для цього окремої таблиці — тобто тієї самої, що вже є.
У `refresh_tokens` зберігається **хеш** токена: дамп бази не має відкривати живі сесії.

Claims access-токена:

```json
{ "sub": "<user uuid>", "iat": 1754270000, "exp": 1754270900 }
```

Ролей поки нема — коли з'являться, додається `role`, і це не ламає наявних клієнтів.

### Що вирішити (?)

**Куди класти refresh.** httpOnly-cookie безпечніша від XSS, але тягне за собою CORS з
`credentials`, `SameSite` і окремий шлях для мобільного клієнта. Тіло простіше і однаково
працює для web і mobile, але токен опиняється в JS.

Пропозиція: **тіло** на цей тиждень, cookie — окремим рішенням, коли буде зрозуміло, чи є
мобільний клієнт. Формат відповіді від цього не змінюється, змінюється лише те, звідки
`/refresh` читає токен.

**Бібліотека JWT.** Одна на репозиторій, інакше в `go.mod` опиняться дві. Пропозиція:
`github.com/golang-jwt/jwt/v5` — де-факто стандарт, активно підтримується.

## `POST /api/v1/register`

```json
{ "name": "Ada Lovelace", "email": "ada@example.com", "password": "correct horse battery" }
```

- `email` — нормалізується до нижнього регістру; колонка `CITEXT`, тож регістр усе одно не має значення
- `password` — мінімум 8 символів (`domain.ErrPasswordWeak`); максимум 72 байти **(?)** — обмеження
  bcrypt, для argon2id не потрібне, але корисне як захист від великих тіл
- `name` — 1–100 символів

**201 Created**

```json
{ "id": "0198f3a0-...", "email": "ada@example.com", "name": "Ada Lovelace" }
```

Реєстрація токенів **не** повертає — користувач далі йде на `/login`. **(?)** Альтернатива —
одразу віддавати пару, щоб не змушувати логінитись двічі. Це зручніше, але змішує два
usecase-и; якщо погодимось, `register` повертає те саме тіло, що й `login`.

Наявний [`register/dto.go`](../internal/user/register/dto.go) повертає `{id, email}` без
`name` — після узгодження треба привести до одного вигляду.

**409** `email_already_exists` — ловиться обмеженням БД, не попереднім `SELECT`: тільки так дві
одночасні реєстрації на одну адресу безпечні.

## `POST /api/v1/login`

```json
{ "email": "ada@example.com", "password": "correct horse battery" }
```

**200 OK**

```json
{
  "access_token": "eyJhbGciOi...",
  "refresh_token": "3Q8f_1kZ...",
  "token_type": "Bearer",
  "expires_in": 900,
  "user": { "id": "0198f3a0-...", "email": "ada@example.com", "name": "Ada Lovelace" }
}
```

`expires_in` — секунди до кінця access-токена, щоб клієнт не парсив JWT заради `exp`.

**401** `invalid_credentials` — **однаково** для «немає такого email» і «невірний пароль».
Різні відповіді перетворюють форму логіну на інструмент перевірки, хто зареєстрований.
З тієї ж причини, якщо користувача не знайдено, перевірка пароля все одно виконується проти
фіктивного хеша: інакше різницю видає час відповіді.

Акаунт, створений через OAuth, має `password_hash IS NULL` і на логін паролем отримує той самий
`invalid_credentials`. **(?)** Можна віддавати підказку «увійдіть через Google», але це знову
розкриває існування акаунта.

## `POST /api/v1/refresh`

```json
{ "refresh_token": "3Q8f_1kZ..." }
```

**200 OK** — те саме тіло, що в `/login`, з **новою** парою: старий refresh відкликається
(`replaced_by` вказує на новий).

**401** `invalid_refresh_token`.

**Пред'явлення вже відкликаного токена — це ознака крадіжки.** Правильна реакція не «відмовити»,
а відкликати весь ланцюжок сесій користувача: якщо один і той самий refresh використали двічі,
значить копія токена є в когось ще, і чинна сесія теж скомпрометована.
